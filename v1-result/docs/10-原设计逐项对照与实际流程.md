## 1. 第 1 题的三次更新怎样接入搜索

题目有两个递推数列：一个从 1 开始每次加 2，另一个从 0 开始累加前者；要证明它们分别等于 `2*n+1` 和 `n*n`。搜索输入只有题目及假设，未提供参考证明。

| 搜索阶段 | 模型更新与后续搜索 |
|---|---|
| step 8 | 根据当前搜索反馈进行第 1 次训练：v0→v1 |
| step 9 | 使用 v1 生成候选；随后第 2 次训练：v1→v2 |
| step 10 | 使用 v2 生成候选；随后第 3 次训练：v2→v3 |
| step 11 | 使用 v3 生成候选，完成证明 |
| 搜索结束后 | 导出生成的证明，在断网 CPU 容器中重新运行 Lean，验证通过 |

三次训练都发生在题目尚未证明时，最终解题奖励均为 0；训练信号来自已有的搜索访问次数和回传值。实际参数变化、每个新版本的后续调用和最终证明都已核验。

搜索协调执行窗口为 **123.062 秒**，从 session 创建与前快照完成后开始，到后快照前结束。创建及回执恢复另约 104.6 秒，独立证明复核另约 52.303 秒；模型下载、环境准备和前后快照也单独计算。

### 一轮 TTT 具体做什么

TTT（测试时训练）是模型在解当前题目时，利用搜索信息更新一小部分参数，再继续解题。

| 顺序 | 实际操作 | 作用 |
|---|---|---|
| 1. 生成 | GPU 根据当前目标提出候选证明步骤，并估计状态价值 | 提供可搜索的方向 |
| 2. 检查 | CPU 上的 Lean 执行候选，记录成功、失败和新的子目标 | 判断候选是否有效 |
| 3. 汇总 | MCTS 选择和展开分支，累计访问次数，把下层估值向上传递 | 得到后续搜索依据及训练数据 |
| 4. 训练 | 在检查点暂停搜索，GPU 根据合格样本更新 LoRA 和价值头 | 调整候选生成策略和状态估值 |
| 5. 继续 | 更新回执确认新版本后，恢复同一 Lean 进程、同一棵搜索树 | 让本题后续搜索用上新参数 |
| 6. 验证 | 找到完整证明后交由 Lean 检查，再独立复验导出的证明 | 确认证明成立 |

第 5 步回到第 1 步，直到证明成功或达到搜索上限。每个检查点只有存在合格搜索样本时才训练；题目提前解出就结束。[原文10：MCTS与TTT](https://github.com/wufuju2023-cell/reap-rsi-public/blob/829829c9c9e69430f273716df92099e3b7d6f748/explain/10-mcts-usage-and-alternatives.md)

### 当前采用的训练方法

- **LoRA** 是附在大模型上的少量可训练参数，7B基座保持冻结；**价值头**负责估计当前证明状态的前景。
- 策略训练按候选访问次数分配权重；价值训练使用搜索回传的估值；另用冻结模型作为参照，约束更新幅度。这是本次选择的搜索蒸馏路线，PPO/GRPO不属于本次必需实现。
- Reap先平均距离、再转换为价值训练目标，这里保留了这一近似。数学定义见[01-实验设计](01-实验设计与成功边界.md)。
- 各题共享冻结的7B基座，训练状态各自独立；GPU按顺序处理模型调用。跨题继承需要另外定义从已完成题目向新题传递参数的规则。
