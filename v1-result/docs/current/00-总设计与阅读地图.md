# TTT框架的组成与学习流程

## 从一道题开始

这个框架希望模型在解题过程中积累经验，并把经验用于后续尝试。输入是一道用Lean写出的数学命题、允许搜索和训练的预算，以及本次使用的模型版本。

当前应用场景是数学证明。模型提出下一步证明并评估当前状态，Reap负责安排搜索顺序，Lean执行步骤、检查最终证明。Reap是框架中的搜索组件；训练、经验保存、版本发布和多题调度由外围程序负责。约70亿参数的基础模型保持不变，训练只更新小规模附加参数（LoRA）和负责状态估值的价值头。

## 有两种学习方式

**一边解当前题，一边训练。** 搜索暂时没有找到完整证明时，也会留下候选步骤的访问次数和状态估值。程序用这些反馈更新本题的参数，收到更新确认后，让原来的Lean进程和原来的搜索树继续。已经有一道题连续使用三次更新后的参数，最后完成证明。见[题内训练流程](01-题内在线TTT.md)和[三次更新后证明的实例](04-实际实例与验收结果.md#same-tree-three-updates)。

**把已验证的证明汇总起来训练。** 每个搜索任务从头到尾使用一个固定发布版本。找到证明或反证后，先保存结果、释放该任务占用的模型状态，再独立检查完整证明并逐步重放。中央训练程序只接收验收通过的证明步骤，训练后发布新参数，供后续任务使用。数学库原有证明也可以加入训练。见[跨题经验与中央训练](02-跨题经验与中央学习.md)和[证明回流实例](04-实际实例与验收结果.md#proof-training-loop)。

这两种方式的训练目标和价值头含义不同，不能直接混用参数。下面表示可选择的两条路线，不表示所有历史实验都跑过每个环节。

1. 题内路线：搜索反馈 → 更新本题参数 → 确认新版本 → 原树继续。
2. 中央路线：固定版本搜索 → 保存结果并释放模型状态 → 独立验证 → 中央训练 → 发布参数 → 后续新任务使用。

## 共享参数与独立状态

同一个模型服务可以共享只读的基础模型。每道题的可训练参数、优化器进度、随机数状态、训练缓存和搜索树分别保存；一道题更新，不会顺带修改其他题。

跨题共享的是已经发布、不能再改写的参数。新题复制这些参数后，重新建立自己的学习状态。本题训练次数从零开始：即使继承的是第二个发布版本R2，本题仍从v0开始。这里的R表示发布版本，v表示本题已经完成的更新次数。

恢复原训练与开始新题也有区别。恢复需要完整检查点，包括参数、优化器、随机数状态、数据采样位置和操作记录；开始新题只复制获准参数。导入前会核对基础模型、训练目标、价值含义和参数形状，不兼容就拒绝。

题目之间可以并行，单个模型服务内部仍按顺序操作可变状态。目前已经实际运行同一张GPU上的两个独立模型服务，各自连接一棵Lean搜索树。新发布版本只影响后来启动的任务，正在搜索的任务保持原版本。详见[并发与版本同步](03-并发调度与模型同步.md)。

## 实际结果与阅读顺序

可以先看[实例结果](04-实际实例与验收结果.md)，再按兴趣阅读题内训练、中央训练和并发同步。实例包括同树三次更新、三题继承同一经验后证明、生成证明回流训练、每批混合两种证明来源，以及双服务并行搜索。

发布同步的最新验收分成两个阶段：原运行完成两次训练、发布和新任务预约后，因子服务等待超时退出；随后用已保存状态完整恢复旧版本，并让新版本实际推理，独立恢复通过。原失败保留，恢复没有重复训练或发布。见[发布与恢复实例](04-实际实例与验收结果.md#published-version-recovery)。

这些结果证明了相应机制已经运行。目标变体课程按用户要求暂停；本轮不追加成功率或不训练对照。长期服务、其他设计缺口及GPU容器的实际范围统一列在[待办](06-待办与验收范围.md)。
