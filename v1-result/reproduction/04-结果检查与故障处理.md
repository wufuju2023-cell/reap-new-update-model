# 结果检查与故障处理

每次实验使用本次实际输出。历史证明、参数哈希和成功回执用于对照，不替代新运行的检查。

## 1. 单题TTT

在本题输出目录检查`online-result.json`：完整证明标志`root_verified`为真，实际更新次数`optimizer_updates`大于0，`online_update_consumed_by_later_generation`为真，并且`error`为空。`learn_receipts`和`post_update_generations`记录训练版本与后续生成的关系。

随后按[单题教程](01-单题TTT.md)提取本轮生成证明，在独立断网容器重新编译并检查公理依赖。保存证明文件、检查命令、容器镜像ID、实际退出码和检查输出。

保留`session.json`、`create-receipt.json`、`observer.jsonl`、`checkpoints/`、`result.json`、`online-result.json`、`snapshot-before.json`、`snapshot-after.json`及标准输出。GPU目录中对应的完整快照另行保存；小型JSON回执记录快照位置，完整参数文件留在GPU机器。

如果零更新即完成证明，这次证明搜索成功，题内训练循环尚未触发。如果预算耗尽，记录未解与已经执行的更新。新运行的更新次数和耗时以实际日志为准。

## 2. 跨题经验复用

先完成来源的独立证明检查，确认有真实更新及`experience-candidate.json`。按[跨题教程](02-跨题经验复用.md)将验收记录绑定到这个来源，提交一次经验发布，保存发布意图与回执。

新题的创建记录必须包含明确经验ID、参数哈希与来源快照哈希。初始化时本题更新计数从0开始，题目ID与来源题不同；起始附加参数和价值头与所选经验一致。之后的新题更新不修改来源或其他题。详细张量核对按教程在GPU机器进行，不需要把大快照下载到CPU。

验收分为三部分：来源正确且不可变、新题确实继承并保持独立、新题最终证明通过独立Lean检查。保存经验发布目录、来源与目标的快照核对结果、两题证明与独立检查回执。

发布来源和恢复原题是两个操作。跨题只复制获准参数；原题完整恢复还需要优化器、随机状态等完整检查点。

## 3. 多题并发

[并发教程](03-多题并发.md)给出的检查命令同时读取`run-exit.json`与`native/campaign-report.json`。要求退出码为0、两个命题分支都独立验证、两条模型服务路由均实际使用。本批新训练次数应为0，因为搜索使用固定发布版本。

GPU侧保存两个真实服务进程的PID、各自日志和快照目录。两个地址若实际指向同一进程，就没有完成双服务部署。CPU侧保存各题预检、搜索、独立验证的容器记录及输出。

同时使用两个服务和实际时间重叠分别核对。便携入口验证两服务路由与两题结果；需要报告本轮重叠时长时，再从两题事件记录计算实际时间区间。历史约7秒重叠或固定请求约1.93倍速度仅属于各自的旧实验。

## 4. 常见问题的处理顺序

| 现象 | 处理 |
|---|---|
| 新输出目录已经存在 | 查看原意图、进程和结果；需要另一次实验时使用新目录 |
| 模型服务健康检查失败 | 先查GPU服务日志、进程和CPU可达地址，不启动Lean搜索 |
| 来源版本不兼容 | 核对模型、价值目标、折扣或类别范围和参数形状；使用匹配服务配置 |
| 搜索已成功，独立复验失败 | 保留原证明与错误，检查完整命题、环境版本和导出过程，不发布经验 |
| 训练请求超时或断联 | 保留原请求编号和回执目录，查询原执行；结果未知时不重训 |
| 发布请求超时 | 检查原发布仓库和请求意图，不通过再次训练生成另一份来源 |
| CPU镜像ID或预检身份不匹配 | 使用实际镜像重新预检；双服务教程的新镜像需显式重新绑定 |
| 新镜像与浏览器桥的固定会话白名单冲突 | 按并发教程的访问方式限制处理；保留白名单检查，不临时放行全部会话 |
| Windows路径过长或WSL挂载路径不合适 | 报告放短路径，CPU运行目录放Linux原生`/home/...` |

## 5. 本次实验的最小总结

写明使用的代码包哈希、模型revision、CPU镜像ID和GPU环境；分别描述每条流程的输入、实际步骤、结果及证据位置。把本地准备测试、真实模型执行和独立Lean验证分开列出。

完成后保存GPU上的完整模型继续点和参数经验。确认没有仍在执行的实验，再正常停止自己的服务和实例。报告不携带这些大文件，后续恢复前要核对它们是否仍存在。
