# 多题并发复现：两个独立7B服务与Lean证明搜索

本流程让两道题分别使用同一张GPU上的两个独立模型进程。每个进程独立加载7B模型、适配器和会话状态；各进程内部仍串行操作模型，两个进程之间可以并行。CPU侧负责题目分配、Lean搜索和独立证明验证。

本章复现的是**固定参数版本的多题证明采集**：每题开始前确定来源版本，搜索中不训练、不切换版本。它与单题内边搜索边更新的TTT是两种运行方式；单题TTT入口见[环境与代码准备](00-环境与代码.md)所列分章。这里不把双进程采集说成多路同时训练。

## 1. 前置环境与目录

先完成[环境与代码准备](00-环境与代码.md)。使用交付包中已校验解压的源码，命令入口为[portable_lean.py](../source/current/portable_lean.py)，它调用既有调度、路由、采集和独立验证模块。

| 位置 | 必需条件 |
|---|---|
| GPU宿主 | 可运行固定REAL-Prover模型的ROCm、PyTorch、Transformers、PEFT环境；已有模型目录；足够同时加载两份模型的显存和主机内存 |
| GPU数据 | 已提取并通过严格加载检查的证明数据，以及本次使用的完整参数发布仓库；两个服务读取同一来源 |
| CPU宿主 | 原生Linux或WSL的Python、可用的本地Podman服务、已存在的CPU镜像；能直接访问该Podman命名卷的挂载目录 |
| CPU镜像 | 预编译Lean 4.28.0-rc1，已构建的ReapRuntime、Reap.VerifiedCollector和相关Mathlib模块；默认项目目录为`/opt/reap-runtime` |
| 网络 | CPU宿主能访问两个不同的GPU服务地址；服务只暴露给受信的本地连接、隧道或桥接 |

CPU镜像的构建入口见[Docker说明](../docker/README.md)。GPU镜像不是本流程的硬前提：历史GPU服务运行在宿主隔离Python环境中，AMD平台上缺少容器服务的问题与本地镜像构建结果分开记录。

CPU运行输出必须位于原生Linux文件系统，例如用户主目录下的`$HOME/reap-runs`。当前脚本拒绝`/mnt/`开头的输出路径，包括`/mnt/c`；准备包可以从Windows文件系统读取，实际运行目录不能放在那里。Podman命名卷也必须位于原生Linux文件系统。调度器会直接读取卷挂载点，使用Windows上的远程Podman客户端不能满足这个条件；应在能操作卷目录的同一Linux上下文运行整个批次。

历史固定请求测试中，每个模型进程峰值已分配显存约15.642GB。这只是该组输入的实测值，不是通用最低显存保证；开始前仍需按实际设备、模型和输入长度检查余量。不要同时保留不需要的训练进程占用GPU。

## 2. 准备自己的参数发布版本

交付包不含模型权重和大型训练检查点。历史版本哈希只能帮助核查旧证据，不能代替用户自己的完整参数仓库。

若已经按[当前复现入口](../source/current/README.md)的混合学习步骤完成训练，可直接使用其成功输出，跳过下面的训练命令。若尚无可用版本，在GPU宿主使用该入口生成一次：

```bash
# 沿用00章GPU终端的GPURUN、MODEL、GPUPY。
# DELIVERY_GPU指向已传到GPU机器的v1-result目录。
set -eu
DELIVERY_GPU=/existing/v1-result
CODE_GPU="$GPURUN/source"
DATA_GPU="$GPURUN/proof-data"
MODEL_GPU="$MODEL"
MIXED_OUT="$GPURUN/mixed"
GPU_PYTHON="$GPUPY"

# 首次提取完整证明数据；已有目录时跳过提取，只做严格复核。
if [ ! -e "$DATA_GPU" ]; then
  "$GPU_PYTHON" -B "$DELIVERY_GPU/source/current/reproduce.py" prepare \
    --source-root "$CODE_GPU" --data-root "$DATA_GPU"
fi
"$GPU_PYTHON" -B "$DELIVERY_GPU/source/current/reproduce.py" check \
  --source-root "$CODE_GPU" --data-root "$DATA_GPU"

# 不加--run只打印计划；确认新输出目录及GPU余量后，再显式执行下一条。
"$GPU_PYTHON" -B "$DELIVERY_GPU/source/current/reproduce.py" mixed \
  --source-root "$CODE_GPU" --data-root "$DATA_GPU" \
  --model-path "$MODEL_GPU" --output "$MIXED_OUT"

"$GPU_PYTHON" -B "$DELIVERY_GPU/source/current/reproduce.py" mixed \
  --source-root "$CODE_GPU" --data-root "$DATA_GPU" \
  --model-path "$MODEL_GPU" --output "$MIXED_OUT" --run
```

最后一条会实际训练两次，每批9条模型生成的证明步骤和1条数学库原有步骤，并检查中间完整恢复。**已有输出或启动意图时不要再次执行。** 若失联，先核对原进程、退出回执和报告，不能用重跑来判断上次是否成功。

该入口的完整输出包括`report.json`、`final-continuation.json`、`learner-store/`，以及输出目录旁的`mixed.exit.json`。从本次成功报告读取第二版参数哈希：

```bash
RELEASE_SHA=$(
  "$GPU_PYTHON" -B - "$MIXED_OUT" <<'PY'
import json, pathlib, sys
p = pathlib.Path(sys.argv[1])
r = json.loads((p / 'report.json').read_bytes())
e = json.loads(p.with_name(p.name + '.exit.json').read_bytes())
c = json.loads((p / 'final-continuation.json').read_bytes())
assert e['returncode'] == 0 and r['ok'] is True
assert r['gates'] and all(v is True for v in r['gates'].values())
assert c['stage_passed'] is True
release = r['release2']['model_release_sha256']
assert c['release_sha256'] == release
print(release)
PY
)
printf '本次固定参数版本：%s\n' "$RELEASE_SHA"
```

两个服务的发布仓库都使用`$MIXED_OUT/learner-store`，不能只复制单个权重文件或把哈希字符串当作仓库。它还包含来源、完整检查点和提交记录，加载时会严格校验。保持原仓库只供读取，并保存其原目录。

下面的服务参数对应上述`mixed`入口：混合模型、价值类别上限8、更新后KL阈值100、默认逐词元评分。若改用其他配置或另一类发布仓库，必须逐项匹配其来源合同；本章不通过放宽校验兼容其他版本。

## 3. 启动两个独立GPU服务

在GPU宿主的两个终端分别运行下列命令。每个终端先设置上一节的实际路径；第一个设置`REPLICA=0`，第二个设置`REPLICA=1`。建议先等第一个服务就绪，再启动第二个，避免同时加载给主机内存和存储造成额外压力。

```bash
# 两个终端分别设为0、1；SERVICE_ROOT是本次新目录。
set -eu
REPLICA=0
SERVICE_ROOT="$GPURUN/two-services"
PORT=$((8761 + REPLICA))
SERVICE_DIR="$SERVICE_ROOT/service-$REPLICA"

test ! -e "$SERVICE_DIR" || { echo '已有服务目录，先检查原进程与回执'; exit 1; }
mkdir -p "$SERVICE_ROOT"
mkdir "$SERVICE_DIR"
cd "$CODE_GPU"

"$GPU_PYTHON" -B -m gpu_runtime.server \
  --host 127.0.0.1 --port "$PORT" --backend mixed-replay \
  --model-path "$MODEL_GPU" --device cuda:0 \
  --verified-dataset-root "$DATA_GPU/replay" \
  --mathlib-dataset-root "$DATA_GPU/mathlib" \
  --verified-max-distance 8 --max-post-update-kl 100 \
  --policy-scoring tokenwise --max-resident-sessions 1 \
  --learner-release-root "$MIXED_OUT/learner-store" \
  --snapshot-root "$SERVICE_DIR/snapshots" \
  >"$SERVICE_DIR/server.log" 2>&1 &
SERVER_PID=$!
printf '%s\n' "$SERVER_PID" >"$SERVICE_DIR/server.pid"
set +e
wait "$SERVER_PID"
SERVER_EXIT=$?
printf '{"returncode":%s}\n' "$SERVER_EXIT" >"$SERVICE_DIR/server-exit.json"
exit "$SERVER_EXIT"
```

等待期间终端保持运行。日志中出现`"ready": true`后，另一终端可对`http://127.0.0.1:8761/health`和`http://127.0.0.1:8762/health`做只读检查。两个服务应有不同的实际PID；仅有两个地址或两份部署标签，不能证明背后是两个模型进程。

本命令启动长期HTTP服务，没有历史联合验收脚本中的900秒子服务控制等待。它不会自动停止闲置实例；批次完成并保存证据后，由操作者正常停止服务与实例。

## 4. 配置CPU可达的两个地址

两种常见连接方式：

- CPU与GPU位于同一Linux主机：可直接使用`http://127.0.0.1:8761`、`http://127.0.0.1:8762`。
- CPU在另一台主机：先建立获准的隧道或桥接，再传CPU主机上可达的两个地址。例如本地18767映射到GPU服务8761，本地18768映射到8762。

服务默认绑定GPU宿主回环地址，不会自动对外开放。历史ModelScope实验使用Edge、OpenCLI与双桥接；这些连接不由`portable_lean.py`创建，不能只照抄端口就假定已连通。

**使用自行构建的新CPU镜像时，本章当前可直接执行的通道是可信直连或已经获准的SSH隧道。** 严格会话白名单桥还有第5节所述的两阶段衔接限制，不能在准备后随意扩大白名单来避开。

搜索容器使用`network=host`，其回环地址属于运行Podman的Linux主机。若桥运行在Windows而Podman运行在WSL，必须先确认WSL能访问所填写的地址。CPU侧健康检查可用：

```bash
ENDPOINT0=http://127.0.0.1:18767
ENDPOINT1=http://127.0.0.1:18768
curl --fail --show-error "$ENDPOINT0/health"
curl --fail --show-error "$ENDPOINT1/health"
```

检查两个响应均成功，后端为`mixed-replay`、会话容量为1。健康响应只证明服务可达；真正的来源参数、完整配置和新会话状态检查在创建会话时完成。

## 5. 准备两题与执行计划

输入已附在[便携模板](../source/current/lean_campaign/README.md)中，无需手写证明：

| 尝试 | 搜索目标 |
|---|---|
| 正向证明 | `∀ n : Nat, n = n` |
| 反驳原命题 | 证明完整否定`¬ (∀ n : Nat, n = 0)` |

每题最多8步，合计16步、最多2次尝试。固定种子用于覆盖正向与反向两种分支，不是随机成功率评测。程序在搜索前展开原命题定义以显示数学内容，展开不提供证明，也不计为模型生成步骤。

在CPU宿主设置本地路径。把GPU报告打印的完整64位版本哈希复制到`RELEASE_SHA`；CPU不需要下载7B模型或大型参数仓库。

```bash
# 沿用00章CPU终端的REPORT、RUN、CPU_IMAGE。
DELIVERY_CPU="$REPORT"
CODE_CPU="$RUN/source"
RUN_CPU="$RUN/two-service-01"
RELEASE_SHA=REPLACE_WITH_YOUR_64_CHARACTER_RELEASE_SHA

# 检查00章选定的实际镜像；不覆盖其标识，也不拉取镜像。
IMAGE_ID=$(podman image inspect "$CPU_IMAGE" --format '{{.Id}}')
IMAGE_ID=${IMAGE_ID#sha256:}

# 默认适用自行构建的镜像：显式建立新的环境身份并重新预检。
python3 -B "$DELIVERY_CPU/source/current/portable_lean.py" --prepare \
  --source-root "$CODE_CPU" --output "$RUN_CPU" \
  --image-id "$IMAGE_ID" --rebind-cpu-image \
  --endpoint "$ENDPOINT0" --endpoint "$ENDPOINT1" \
  --deployment-id my-run-replica-0 --deployment-id my-run-replica-1 \
  --release-sha256 "$RELEASE_SHA" --project-dir /opt/reap-runtime

python3 -B "$DELIVERY_CPU/source/current/portable_lean.py" \
  --check --output "$RUN_CPU"
```

两份部署标签由操作者分配，必须不同，并与本次两个真实服务对应。它们用于固定路由，不是认证凭据，GPU服务也没有`--deployment-id`参数。

`--prepare`和`--check`不调用GPU、网络、Podman或Lean；它们检查输入与代码，复制本次固定源码并生成计划。新镜像模式此时仍处于待预检状态，尚无最终会话标识。实际执行时，两道题的断网编译都通过后，才生成最终计划并创建GPU会话。准备后不要手改计划、题目或源码，哈希不一致会拒绝执行。

若本机确实保留原实验镜像，且实际ID为`d2070a64912f1a7c66ec9e4bb92e66004e8adaa58887e7be333f0bf8e3d5f3b7`，可省略`--rebind-cpu-image`，保留原输入环境身份；两次实际预检仍会执行。新镜像即使标签相同，也必须按实际ID走重新绑定。该入口暂不支持随意改成更多题，改题需要新的声明与预检材料。

### 严格会话白名单桥的配置边界

若使用原镜像模式，准备阶段已经确定本次两个新会话标识。先从计划读取它们，再按00章配置两个桥，各桥均明确列出这两个标识，分别转发到8761和8762：

```bash
python3 -B - "$RUN_CPU/plan.json" <<'PY'
import json, pathlib, sys
p = json.loads(pathlib.Path(sys.argv[1]).read_bytes())
attempts = p['expected_attempts']
assert len(attempts) == 2, '新镜像尚未完成预检，当前没有可填写的会话标识'
for a in attempts:
    print('--session-id', a['attempt_id'])
PY
```

桥启动参数中的`--session-id`逐项使用这里的新值，不能使用旧实验标识。两个桥使用不同本地端口和远端作业目录，并分别指定`--target-port 8761`、`--target-port 8762`；其余当前浏览器、实例与脚本路径按00章配置。所有请求仍由桥逐项核对会话白名单，服务分配记录则限定每题只使用其中一个服务。

新镜像模式在真实预检前没有最终会话标识，当前`--run`又会在预检完成后立即派发搜索，没有可供操作者配置白名单的暂停接口。因此“仅能使用此桥、同时只有新镜像”的组合尚不能用本入口原样运行。可使用已保留的原镜像完成上述步骤，或使用实际可用的可信直连/隧道；若平台两者均不具备，应先补充并验收“只预检→配置精确白名单→继续”的入口，再开始GPU搜索。不能移除镜像绑定、伪造预检收据、使用通配会话或抢在首请求前修改白名单。

## 6. 单次执行与保存输出

确认两个GPU服务和CPU连接均已就绪，CPU镜像存在，输出位于原生Linux目录后执行一次：

```bash
python3 -B "$DELIVERY_CPU/source/current/portable_lean.py" \
  --run --output "$RUN_CPU"
```

程序依次完成：

1. 在两个断网CPU容器中检查Lean环境并预编译两道完整命题。
2. 保存尝试与服务分配记录，最多同时派发两个搜索任务；每题固定到一个GPU服务。
3. 搜索明确结束后保存完整材料，向原服务释放会话；释放回执确认后才腾出容量。
4. 对找到的证明使用断网容器独立检查整个定理、公理依赖及每条证明步骤；只有通过后才安装训练数据包。
5. 保存批次报告、实际退出码和原始输出。验证最多并行1项，等待验证最多占用2个位置。

本章的两题不调用训练接口。新参数只来自第2节已经完成的发布；搜索过程不会回写或更新原参数仓库。

| 输出位置 | 保存内容 |
|---|---|
| `$RUN_CPU/run-intent.json`、`run-exit.json` | 单次启动意图及实际退出码 |
| `$RUN_CPU/run-stdout.log`、`run-stderr.log` | 外层完整输出 |
| `$RUN_CPU/native/campaign-report.json` | 两题独立验证、两服务实际使用及总体结果 |
| `$RUN_CPU/native/batch-report.json` | 搜索、验证、等待阶段及调度结果 |
| `$RUN_CPU/native/containers/` | 各容器的创建命令、检查结果、输出和真实退出码 |
| `$RUN_CPU/collected/volume/sessions/` | 每题源码、搜索事件、创建回执和候选证明 |
| `$RUN_CPU/collected/volume/verified/`、`dataset-store/` | 独立验证回执及通过验证的数据包 |
| `$RUN_CPU/collected/export-manifest.json` | 导出文件哈希；原生目录与命名卷仍保留 |
| GPU的两个`service-N/`目录 | 服务日志、PID、退出回执和释放时的终态快照 |

新镜像的最终计划在命名卷及其导出副本的`runtime-plan.json`中。成功时，导出副本位于`$RUN_CPU/collected/volume/runtime-plan.json`；准备阶段的`plan.json`仍保留原待预检记录。

## 7. 验收与异常处理

最低成功条件是实际退出码与报告同时通过：

```bash
python3 -B - "$RUN_CPU" <<'PY'
import json, pathlib, sys
p = pathlib.Path(sys.argv[1])
e = json.loads((p / 'run-exit.json').read_bytes())
r = json.loads((p / 'native/campaign-report.json').read_bytes())
assert e['returncode'] == 0
for name in ('ok', 'execution_completed', 'both_independently_verified_branches',
             'both_replica_endpoints_used'):
    assert r[name] is True, name
assert r['new_training_steps'] == 0
assert len(r['actual_routes']) == 2
print('两题独立验证及双服务使用通过；本批没有训练。')
PY
```

进一步核查每个搜索、预检、验证容器的回执：Podman退出码与容器退出码都必须为0；独立验证容器网络为`none`。通过验证的数据包必须有完整来源和验证回执，不能仅依据搜索器声称“找到证明”。两个真实GPU进程的身份另从部署PID和服务日志确认。

这个便携入口不会自动测量搜索事件区间的重叠，也没有完整远端张量和原始HTTP通信审计。因此，报告成功说明两题完整执行且两个服务确实被使用；要量化并行收益，还需依据本次实际事件时间单独分析，不能直接套用历史速度比。

若出现已知预算耗尽，结果如实记为未解，本章要求两题通过的总验收不会成功。若启动、搜索或释放结果未知，保留原容器、卷、会话占用及意图，不自动重搜、切换服务或重新训练。已有`run-intent.json`会阻止再次启动；`collected/`也可能在失败时产生，它的存在不代表成功。先检查原进程、容器状态及原回执，再决定后续处置。

全部会话确认释放、输出保存并核对后，再正常停止两个GPU服务。启动终端中的`wait`会记录实际退出码；不要在仍有未知操作时删除服务快照、Podman卷或输出目录。远端实例由操作者按平台流程停止，本脚本不管理实例启停。

## 8. 已有实测与本章说明的验证级别

[历史双服务Lean实验](../evidence/current/replica-collector/README.md)确实运行了两个独立7B进程。两个分支分别得到2条和1条证明步骤，并通过断网整体证明与逐步复验；批次耗时75.318809秒。按搜索日志首末事件计，两个搜索区间重叠7.042941122秒。该结果来自固定输入与历史发布版本，不能保证换用新的参数后仍在8步内得到同一证明。
