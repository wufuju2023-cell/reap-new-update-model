# 运行速度异常事故与强制监控门（2026-08-29）

## 事故

首个课程展示迟迟没有结果。统筹曾把 Codex 执行任务显示为 `active` 当作远端搜索正在运行；实际上 Radeon 长时间保持 `create=0`，ModelScope 虽已 create，却在第一次 8-step learn 后因缺失 `selection_value_refresh` 事件确定性终止。异常由用户先指出，统筹没有及时根据吞吐主动发现。

这不是 GPU 或 TTT 本身慢：ModelScope 的正式失败场在 33.37 秒内完成 8 policy、8 value 和 1 learn；learn 耗时 1.88 秒。真正耗时来自 create 前容器门、无效 runtime 接线和事后诊断。

## 根因

1. 把对话任务状态当作进程证据，没有及时要求 session、PID、checkpoint 和请求计数。
2. `selection_value_refresh` 只核了 Python coordinator/driver 的字段与测试；当前 Lean/ReapRuntime 没有产出 `selection_value_refresh` 事件的实现。Python 在 learn v0→v1 后按 fail-closed 合同终止。
3. Radeon 固定 CPU preflight 先以 root 运行，导致 Lake 误判依赖并在 `network=none` 下尝试 clone；镜像实际固定用户是 UID/GID 10001。
4. 对 prepare/preflight 阶段缺少独立延迟预算，使“尚未 create”被过久地描述为“正在运行”。

## 立即生效的监控门

- “已开始实验”只允许在真实 create receipt、session ID、运行 PID 和首 checkpoint/request 至少一项齐全后使用；任务 `active`、preflight、listener health 都不能替代。
- 已就绪服务的 create/首步门：create 后 30 秒内核 PID、actor active/queued 与首个 policy/value 请求；90 秒内必须出现 checkpoint 0 或明确错误。
- 搜索活性门：当前实测约 4–6 秒/step。只要 checkpoint 持续增长，8-step 课程完整自然跑完，16-step 课程也默认放宽到自然终态，不做行为早停或课程调整。只有连续 60–90 秒无任何新 checkpoint，或 PID/unknown/工程错误异常，才立即只读核最后进度、请求 outcome/耗时、GPU actor、relay 和 stderr。
- learn 后消费门：learn receipt 返回后 30 秒内，若 refresh 开启必须看到 refresh 事件；若 refresh 关闭，必须在下一个完整生成窗口看到 v+1 generation/value 前向。否则立即诊断并安全停止。
- 任何新 runtime 能力在正式开启前，必须同时找到 producer（Lean/搜索侧事件产生）和 consumer（Python/审计侧验证）的真实实现与最小贯通门；只有 schema/传参/单元测试不够。
- 工程失败 session 不重试、不覆盖；先核 unknown/pending=0，snapshot/retire，再用新 immutable ID 且只改变一个有证据的工程变量。
- 统筹在首 checkpoint 前最多每 30 秒主动取一次紧凑状态；这只是活性观察，不是干预。首 checkpoint 后按完整 8-step/update 窗口收摘要，16-step 内若持续推进则等待自然终态。用户不应再承担首先发现停滞的职责。

## 当前纠偏

- ModelScope 旧 refresh 场已 snapshot、receipt-backed retire，unknown=0；新 D3 session 使用稳定的 `selection_value_refresh=false` 合同。LoRA 与 categorical value head 仍联合更新，必须核更新后新 generation/value 的真实消费；旧节点缓存不刷新单列为限制。
- Radeon refresh 场已确认所有请求 returned、unknown=0；只允许一次 v1 snapshot 后 retire，不继续该 session。
- 本事故不计模型失败，不进入成功案例目录。
