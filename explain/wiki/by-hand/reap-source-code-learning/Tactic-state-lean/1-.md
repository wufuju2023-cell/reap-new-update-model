6. The signature
def containsDefEqType (types : Array Expr) (type : Expr) : MetaM Bool
- Expr — the inductive type of Lean terms: inductive Expr where ... (lean4/src/Lean/Expr.lean:298). Constructors include .bvar (de Bruijn bound var, line 299-303), .fvar, .mvar (metavariable), .const, .app, .lam, .forallE, .letE, .sort, .lit, .mdata, .proj. Note it's a tree over names and indices, no binding structure — the letE/lam carry the binder explicitly.
- Array Expr — persistent, functional array (Std.Data.Array), grown via .push. Here: the set of types already seen during the scan.
- MetaM Bool — the crucial piece. Its definition, lean4/src/Lean/Meta/Basic.lean:596:
abbrev MetaM := ReaderT Context $ StateRefT State CoreM
Layer by layer, innermost first:
- CoreM = StateRefT Core.State IO-based — the base monad carrying the environment, options, message log, and error handling with state rollback (exceptions discard the state, so operations like isDefEq can backtrack).
- StateRefT State — Lean.Meta.State holds the metavariable assignment state (mctx: which ?m is assigned to what) and the defeq/transparency caches. This is mutable state accessible during the computation.
- ReaderT Context — structure Context (lean4/src/Lean/Meta/Basic.lean:492): environment, local context (lctx), transient context, and importantly the defEqCtx? used by defeq.
So MetaM Bool = "a computation that reads the meta context, can mutate metavariable assignments, may throw errors (caught and rolled back), and returns a Bool".
- Bool — the return type: yes/no answer.

8. isDefEqGuarded — the meat
Definition, lean4/src/Lean/Meta/Basic.lean:2546-2551:
def isExprDefEqGuarded (a b : Expr) : MetaM Bool := do
  try isExprDefEq a b catch _ => return false

abbrev isDefEqGuarded (t s : Expr) : MetaM Bool :=
  isExprDefEqGuarded t s
First, isDefEq / isExprDefEq (lines 2507–2544): "Determines whether two expressions are definitionally equal". Critically, the docstring at 2531–2542 explains the semantics:
metavariables and their context have a "depth". Given a metavariable ?m and its context, ?m is not assigned if ?m.depth != mctx.depth. withNewMCtxDepth x bumps the depth while executing x. So withNewMCtxDepth (isDefEq a b) is isDefEq without any mvar assignment happening, whereas isDefEq a b will assign any metavariables of the current depth in a and b to unify them.
That is: defeq is not only a boolean check — it's an unification that can assign metavariables as a side effect (e.g. ?m := 2 when comparing ?m with 2). The assignment lands in Meta.State.mctx, hence the need for MetaM to be a State monad at all.
Equality itself is judged definitional, i.e. by conversion (β-reduction, δ-reduction of transparent definitions, ι-reduction of match, proof-irrelevance for propositions, etc.) — not syntactic equality. 2 + 2 and 4 are defeq equal in Nat; ∀ x, P x and ∑ x, P x are not.
Then the Guarded wrapper: try ... catch _ => return false. Defeq can throw (e.g. on assignments validation failures, unexpected expression errors) — the wrapper guarantees the function never bottoms out; it degrades to "not equal" on any exception. Check how it's used in the core: Lean/Meta/Structure.lean:144 (unless ← isDefEqGuarded p1 p2) and Lean/Meta/Check.lean:231 — a "safe test" idiom, an exception means "cannot prove equal", hence false.
9. What this function is actually for (in Reap)
Look at the other two defs in the same file: duplicatePropFVarIds (lines 17–28) iterates the local context; for every local hypothesis whose type is a proposition, if containsDefEqType seenTypes type returns true, the hypothesis is marked as a duplicate — then dedupPropContext (line 30–32) calls goal.tryClearMany on all duplicates.
Why is the definitional comparison the right one? Two local hypotheses h1 : P, h2 : P' with P ≃def P' are mutually substitutable — any proof of P converts to a proof of P', so keeping both adds zero information. Dropping the duplicate is sound. And dedupPropContext is called by simplifyState (line 34), used by Reap's state handling as a canonicalization step:
- it shrinks the LLM prompt (proof state is pretty-printed and sent to the policy model — Tactic/Generator.lean:146-155), less context noise = better generations for the same tokens;
- it makes the StateKey hash (Reap/Tactic/State.lean:42-46, JSON of printed goals) canonical, which is how MCTS dedupes identical proof states (Tactic/TreeSearch.lean:279: if !ancestorKeys.contains childData.key).
So one tiny helper — a few dozen times per context — sits at the exact load-bearing point that makes MCTS's state deduplication work without doing unification the hard way.
Takeaway line
containsDefEqType types type : MetaM Bool = "does type already appear (definitionally, modulo unification) in types?" — implemented as a linear scan with Lean's guarded defeq checker, used as the primitive for sound local-context deduplication before LLM prompting and state hashing. It is also your gateway example of the Lean meta API: MetaM is kinda a Read+Write+Throw monad over elaboration state, and isDefEqGuarded is the "safe unification" primitive — genuinely the same thing rfl/exact use internally, just wrapped to never fail.
